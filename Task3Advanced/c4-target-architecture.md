# Целевая архитектура «Будущее 2.0» — горизонт 3 года

C4-модель на уровнях **System Context** (L1) и **Container** (L2). Архитектура построена на принципах **Data Mesh** и **Event-Driven Architecture** в облачной инфраструктуре Yandex Cloud.

## 1. System Context (C4 Level 1)

Контекстная диаграмма показывает целевую систему «Будущее 2.0» и её взаимодействие с внешними акторами и системами.

**Ключевые изменения относительно текущей архитектуры (AS-IS):**

| AS-IS (сейчас) | TO-BE (3 года) |
|---|---|
| Файловый обмен через Excel и общие папки | Единая событийная шина (Kafka), API |
| Монолитный DWH на SQL Server 2008 | Data Mesh: доменные Data Products |
| 1С и ККМ как отдельные системы | Интегрированы в домены через API-слой |
| Нет самообслуживания для аналитики | Портал Self-Service BI |
| Интеграции через Apache Camel | События + антикоррупционные слои (ACL) |

## 2. Container Diagram (C4 Level 2)

Детализация целевой платформы на уровне контейнеров (доменов и инфраструктурных сервисов).

**Пояснение ключевых контейнеров:**

| Контейнер | Назначение | Почему выбран |
|---|---|---|
| **Event Bus (Kafka)** | Асинхронная коммуникация доменов. Замена шины Camel | Гарантированная доставка, replay, партиционирование |
| **Schema Registry** | Централизованный каталог схем событий | Предотвращает breaking changes между доменами |
| **DLQ** | Отказоустойчивость: недоставленные события не теряются | Критично для медицинских и финансовых данных |
| **Data Lake / Lakehouse** | Единое хранилище сырых данных всех доменов | Горизонтальное масштабирование, SQL-доступ |
| **Legacy Bridge** | Временный ACL-слой для миграции из DWH | Позволяет мигрировать домены постепенно |
| **BI-портал** | Self-service аналитика без участия IT | Ускоряет time-to-market отчётов с часов до минут |

## 3. Этапы трансформации (roadmap)

Трансформация разбита на три этапа с горизонтом 3 года.

### Этап 1: Пилот (месяцы 0–6)

Цель: проверить целевой подход на 1–2 доменах, запустить базовую инфраструктуру.

| Месяц | Активность | Результат |
|---|---|---|
| 1–3 | Развёртывание Event Bus (Kafka) в Yandex Cloud | Шина готова к приёму событий |
| 3–4 | Подключение Медицинского домена + Финтех-домена | Домены публикуют и потребляют события |
| 4–5 | Внедрение Schema Registry + Dead Letter Queue | Схемы валидируются, сбои не теряются |
| 5–6 | Запуск ACL-слоя для Camel/DWH (Legacy Bridge) | Легаси-данные поступают в шину, домены изолированы от старых форматов |

### Этап 2: Масштабирование (месяцы 6–18)

Цель: расширить на критические домены, запустить Data Lake и потоковые витрины.

| Месяц | Активность | Результат |
|---|---|---|
| 6–12 | Подключение ИИ-домена (ML-модели, GPU) | Предиктивная аналитика и диагностика в потоке |
| 10–18 | Интеграция Фарма-домена и Домена оборудования | Поставки, остатки, телеметрия устройств — в реальном времени |
| 12–18 | Развёртывание Data Lake / Lakehouse (S3 + YDB) | Единое хранилище сырых данных всех доменов |
| 15–18 | Запуск потоковых витрин (Kafka Streams / Spark) | Агрегации и витрины обновляются near-real-time |

### Этап 3: Финал (месяцы 18–36)

Цель: отказ от легаси на критическом пути, полный переход на доменную событийную аналитику.

| Месяц | Активность | Результат |
|---|---|---|
| 18–24 | Отказ от синхронных интеграций через Camel (критический путь) | Все критические потоки — через события |
| 24–30 | DWH переводится в режим cold storage (исторические данные) | DWH больше не участвует в операционной аналитике |
| 30–36 | Self-service BI развёрнут для всех доменов | Бизнес-пользователи строят отчёты без участия IT |
