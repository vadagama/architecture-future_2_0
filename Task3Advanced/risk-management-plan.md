# План управления рисками

Меры по снижению каждого из выявленных рисков. Для каждого риска указано: **техническое** это решение или **управленческое**.

---

## R1. Потеря данных при миграции из DWH

**Тип мер:** Технические + управленческие

| Мера | Тип | Описание |
|------|-----|----------|
| **Инкрементальная миграция по доменам** | Техническая | Переносить данные не «всё сразу», а домен за доменом с верификацией на каждом шаге. Начать с некритичных доменов |
| **Data Reconciliation** | Техническая | Автоматизированная сверка row counts, checksums и бизнес-метрик между DWH и новым хранилищем после каждой волны миграции |
| **Shadow Run (параллельный прогон)** | Техническая | Новые и старые системы работают параллельно 2–4 недели. Сравнение результатов перед отключением легаси |
| **Аудит схем DWH** | Управленческая | Выделить 2–3 недели на реверс-инжиниринг недокументированных хранимых процедур. Привлечь ветеранов команды |

---

## R2. Нарушение целостности при асинхронной коммуникации

**Тип мер:** Технические

| Мера | Тип | Описание |
|------|-----|----------|
| **Idempotency keys** | Техническая | Каждое событие содержит уникальный ключ идемпотентности. Потребители проверяют ключ перед обработкой — исключены дубликаты |
| **Schema Registry + версионирование** | Техническая | Все события проходят валидацию схемы через Schema Registry. Контракты версионируются (forward/backward compatibility) |
| **Outbox Pattern** | Техническая | Запись в БД и публикация события — атомарно через outbox-таблицу. Исключает потерю событий при сбоях |
| **DLQ + алертинг** | Техническая | Недоставленные события попадают в Dead Letter Queue. Автоматический алертинг дежурному инженеру для ручного разбора |

---

## R3. Сопротивление команд и нехватка компетенций

**Тип мер:** Управленческие

| Мера | Тип | Описание |
|------|-----|----------|
| **Программа обучения** | Управленческая | Трёхмесячный onboarding: Kafka, Go, облачные сервисы, Event-Driven. Сертификация по итогам |
| **Центр компетенций (CoE)** | Управленческая | Создать ядро из 3–5 инженеров-лидеров, которые уже имеют опыт. Они менторят остальные доменные команды |
| **Внешний найм на ключевые роли** | Управленческая | Нанять Staff Engineer с опытом Data Mesh и DevOps-инженера с опытом Yandex Cloud. Они задают стандарты |
| **Пилот на одном домене** | Управленческая | Начать с небольшого домена (например, инвентаризация), чтобы команда «потрогала» новый стек без давления. Собрать lessons learned перед масштабированием |

## R4. Срыв сроков миграции из-за сложности легаси

**Тип мер:** Управленческие + технические

| Мера | Тип | Описание |
|------|-----|----------|
| **Strangler Fig Pattern** | Техническая | Не «переписывать всё», а постепенно перехватывать функциональность через новый код. Легаси-система умирает естественно, когда все вызовы переключены |
| **ACL-слой (Legacy Bridge)** | Техническая | Временный антикоррупционный слой адаптирует легаси-интерфейсы к новому API. Домены не зависят от форматов легаси |
| **Буфер в roadmap** | Управленческая | Закладывать +30% времени на каждый этап миграции под «неизвестные зависимости». Не планировать жёсткие дедлайны для вывода DWH |

## R5. Проблемы с производительностью Event Bus

**Тип мер:** Технические

| Мера | Тип | Описание |
|------|-----|----------|
| **Правильное партиционирование** | Техническая | Партиционировать топики по business key (например, `patient_id`). Избегать «горячих» партиций |
| **Load testing до go-live** | Техническая | Провести нагрузочное тестирование с 3× от ожидаемого пика. Настроить автоскейлинг брокеров |
| **Мониторинг (consumer lag, throughput)** | Техническая | Метрики Kafka → Grafana. Алерты при росте consumer lag > N сообщений или падении throughput |
| **Managed Service** | Техническая | Использовать Yandex Managed Service for Kafka, чтобы не управлять кластером вручную |

## R6. Несоблюдение требований регуляторов

**Тип мер:** Управленческие + технические

| Мера | Тип | Описание |
|------|-----|----------|
| **Юридический аудит до старта** | Управленческая | Привлечь юристов по 152-ФЗ и ЦБ РФ для оценки допустимости облачного размещения. Получить письменное заключение ДО начала миграции |
| **Гибридное размещение** | Техническая | Медицинские данные (особо чувствительные) временно оставить в on-premise контуре, в облако вынести менее критичные домены |
| **Аттестованные сервисы** | Техническая | Использовать только сервисы Yandex Cloud, прошедшие аттестацию по ГОСТ и 152-ФЗ. Вести реестр допустимых сервисов |
| **Шифрование + аудит** | Техническая | Все данные в покое и в движении шифруются (ГОСТ-шифрование). Включить Yandex Audit Trails для всех операций |

---

## R7. Фрагментация данных между доменами

**Тип мер:** Управленческие + технические

| Мера | Тип | Описание |
|------|-----|----------|
| **Data Governance Council** | Управленческая | Регулярные встречи Data Product Owner'ов всех доменов. Согласование общих определений (Customer, Product, Transaction) |
| **Централизованный Data Catalog** | Техническая | Каталог всех Data Products с описанием схем, владельцев и SLA. Построить на базе Yandex Data Catalog или Amundsen |
| **Global IDs** | Техническая | Сквозные идентификаторы (UUID) для ключевых сущностей — клиент, пациент, счёт. Единый стандарт именования полей |

## Сводка: какие риски чем закрываются

| Риск | Технические меры | Управленческие меры |
|------|------------------|---------------------|
| **R1** Потеря данных | Инкрементальная миграция, Reconciliation, Shadow Run | Аудит схем DWH |
| **R2** Целостность (async) | Idempotency, Schema Registry, Outbox, DLQ | — |
| **R3** Сопротивление команд | — | Обучение, CoE, найм, пилот |
| **R4** Сроки миграции | Strangler Fig, ACL-слой | Буфер в roadmap |
| **R5** Производительность Kafka | Партиционирование, Load test, Мониторинг, Managed Service | — |
| **R6** Регуляторы | Гибридное размещение, аттестованные сервисы, шифрование | Юридический аудит |
| **R7** Фрагментация | Data Catalog, Global IDs | Governance Council |
