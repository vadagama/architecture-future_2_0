# Обоснование событийного подхода vs Camel/DWH

## Текущее состояние (AS-IS)

Сегодня интеграции в «Будущем 2.0» построены на двух механизмах:

| Механизм | Роль | Проблемы |
|---|---|---|
| **Apache Camel (ESB)** | Синхронная шина данных, маршрутизация между системами | Точка отказа (SPOF), сложность отладки, синхронные блокировки |
| **SQL Server DWH (2008)** | Централизованное хранилище и бизнес-логика | Монолит, часы на формирование отчётов, ограниченное масштабирование |

**Симптомы, которые испытывает бизнес сегодня:**
- Формирование сложных отчётов занимает **часы**.
- Добавление нового бизнес-направления требует **месяцев** интеграции через DWH.
- Бизнес-логика «размазана» по хранимым процедурам DWH — изменения в одном домене ломают отчёты других.
- Camel — синхронный: сбой одного сервиса каскадно останавливает другие.

## Целевой подход: Event-Driven Architecture + Data Mesh

### Что меняется

| Аспект | Camel/DWH (AS-IS) | Событийная шина (TO-BE) |
|---|---|---|
| **Тип интеграции** | Синхронная (request/response) | Асинхронная (publish/subscribe) |
| **Связность** | Сильная (изменение формата ломает всех) | Слабая (схемы версионируются, контракты изолированы) |
| **Владелец данных** | Централизованный DWH | Каждый домен владеет своим Data Product |
| **Масштабирование** | Вертикальное (дороже железо) | Горизонтальное (Kafka-партиции, облачные сервисы) |
| **Отказоустойчивость** | Отказ DWH = остановка всего | Отказ домена = изолирован; DLQ сохраняет события |
| **Time-to-insight** | Часы (batch-отчёты) | Минуты (потоковые витрины) |
| **Добавление домена** | Месяцы интеграции через DWH | Подключение к шине + контракт событий = дни |

### Преимущества для «Будущего 2.0»

#### 1. Гибкость (Flexibility)

Новый домен (например, фарма-компания) подключается к платформе через три шага:
1. Определить контракты событий (Schema Registry).
2. Развернуть доменный контейнер.
3. Подписаться на нужные топики Kafka.

**Без изменений в других доменах.** Сравните с текущим подходом: нужно модифицировать хранимые процедуры DWH, добавить таблицы, обновить Power BI-отчёты, протестировать регрессию по всем существующим сценариям.

#### 2. Масштабируемость (Scalability)

- **Kafka-партиции** распределяют нагрузку по брокерам. При росте трафика достаточно добавить брокеров — без изменения кода доменов.
- **Data Mesh** позволяет каждой доменной команде масштабировать своё хранилище независимо. Медицинский домен может выбрать PostgreSQL, а домен оборудования — TimescaleDB для временных рядов.
- **Облачная инфраструктура** (Yandex Cloud Managed Kafka) снимает с команды задачу администрирования кластера.

Сейчас DWH — монолит: рост данных на 20% требует апгрейда всего сервера и влияет на производительность всех потребителей.

#### 3. Скорость реакции (Responsiveness)

- **Потоковая обработка** (Kafka Streams / Spark): события обрабатываются в real-time. Например, `StockLowAlert` от фарма-контекста мгновенно создаёт заказ поставки, а не ждёт ночного batch-окна DWH.
- **Self-service BI**: бизнес-аналитик строит отчёт через портал за минуты, а не ждёт IT-команду с запросом на SQL.
- **DLQ + мониторинг**: сбой доставки события алертится сразу, а не обнаруживается через день при сверке отчётов.

#### 4. Отказоустойчивость (Resilience)

- **Изоляция сбоев**: если финтех-домен временно недоступен, медицинский домен продолжает работать. События для финтеха буферизуются в Kafka и доставляются после восстановления.
- **Dead Letter Queue**: события, которые не удалось обработать (например, повреждённый формат), не теряются, а попадают в DLQ для ручного разбора.
- **Event Sourcing** (опционально): возможность пересчитать состояние домена, перепроиграв все события с начала. Недостижимо при синхронных вызовах через Camel.

#### 5. Эволюционность (Evolvability)

- **Версионирование схем** (Avro + Schema Registry): контракты меняются без остановки потребителей. Старые версии схем совместимы вперёд.
- **Strangler Fig**: легаси-системы (DWH, Camel) выводятся постепенно. Legacy Bridge публикует события из DWH, домены постепенно переключаются на нативные источники.

## Почему не оставить Camel + DWH

| Аргумент «оставить» | Контраргумент |
|---|---|
| «Camel работает, зачем трогать» | Camel — синхронный SPOF. Как только число доменов вырастет до 5–6, каскадные сбои станут неизбежны. Плюс нет встроенного версионирования контрактов |
| «DWH уже содержит всю логику» | Именно это и есть проблема: логика «вшита» в хранимые процедуры. Изменение в одном домене = регрессионное тестирование всего DWH. Data Mesh разделяет ответственность |
| «Переход на события — это дорого» | Дорого **не переходить**. При росте на 3 региона и 2 новых направления текущая архитектура не масштабируется. Стоимость отказа от трансформации = потеря рынка |
| «Можно просто обновить DWH» | Апгрейд SQL Server до актуальной версии не решает проблему монолита. Данные по-прежнему централизованы, а доменная логика — связана |

## Резюме

Целевая событийная архитектура на базе Data Mesh — не просто «модный тренд», а **архитектурная необходимость** для компании, которая планирует:

- Масштабироваться с 1 региона до 3–4.
- Добавлять 2–3 новых бизнес-направления без переписывания интеграций.
- Сократить time-to-insight с часов до минут.
- Обеспечить независимость доменных команд (каждая владеет своим Data Product и стеком).

Переход на события — это инвестиция в **гибкость, скорость и управляемость** роста компании на горизонте 3+ лет.
