# Стратегический роадмап внедрения Data Mesh

Поэтапный план трансформации компании «Будущее 2.0» к целевой Data Mesh-архитектуре. Каждый этап привязан к бизнес-целям и ролям.

---

## Ключевые роли

| Роль | Ответственность | Когда появляется |
|---|---|---|
| **Data Product Owner (DPO)** | Владелец Data Product в домене. Определяет SLA, качество, roadmap данных. Отвечает за ценность данных для потребителей | Этап 1 (по 1 на пилотный домен) |
| **Data Engineer** | Разрабатывает и поддерживает пайплайны данных, потоковую обработку, витрины. По 1–2 на домен в зависимости от сложности | Этап 1 |
| **BI-аналитик** | Строит отчёты и дашборды через Self-service BI. Формирует требования к витринам и Data Products | Этап 1 |
| **Platform Engineer** | Поддерживает Event Bus (Kafka), Schema Registry, облачную инфраструктуру. Общий для всех доменов (2 FTE) | Этап 1 |
| **Domain Architect** | Архитектор домена: bounded contexts, агрегаты, контракты событий. Один на компанию на старте, затем по 1 на критический домен | Этап 1 |
| **Data Governance Lead** | Ведёт каталог Data Products, согласовывает определения (Customer, Patient, Transaction). Организует Governance Council | Этап 2 |
| **Security/Compliance Officer** | Обеспечивает соответствие 152-ФЗ, ГОСТ, ЦБ РФ в облачной архитектуре | Этап 1 |
| **ML Engineer** | Разрабатывает и развёртывает ML-модели в ИИ-домене | Этап 2 |

---

## Этап 1: Пилот (месяцы 0–6)

### Бизнес-цели
- Проверить работоспособность Data Mesh на 2 доменах.
- Снизить время формирования отчётов по пациентам и финансам с часов до минут.
- Получить опыт команды и lessons learned перед масштабированием.

### Активности

| Месяц | Активность | Роли | Результат |
|---|---|---|---|
| 1–2 | Развёртывание облачной инфраструктуры (Yandex Cloud + Managed Kafka + K8s) | Platform Engineer, DevOps | Базовая платформа готова |
| 1–2 | Запуск Schema Registry, определение стандартов именования событий | Domain Architect | Каталог схем событий |
| 2–3 | Обучение команд: Kafka, Go, DDD, Data Mesh | Все роли | 80% команды сертифицированы |
| 2–4 | Проектирование bounded contexts для Медицинского и Финтех-доменов | Domain Architect, DPO | Границы контекстов, агрегаты, контракты |
| 3–4 | Разработка Data Products: Patient360 (Медицина) и FinancialCore (Финтех) | Data Engineers (2), DPO (2) | Data Products в проде |
| 4–5 | Подключение Legacy Bridge (ACL) для миграции данных из DWH | Data Engineers, Platform Engineer | Легаси-данные поступают в шину |
| 5–6 | Запуск Self-service BI (DataLens) для пилотных доменов | BI-аналитики (2) | Бизнес-пользователи строят отчёты |
| 6 | Ретроспектива пилота. Фиксация lessons learned | Все роли | План масштабирования скорректирован |

### KPI успеха
- Time-to-insight по пилотным отчётам: ≤ 5 минут (сейчас: часы).
- Количество инцидентов при миграции данных: 0 критических.
- NPS бизнес-пользователей пилота ≥ 7/10.

---

## Этап 2: Масштабирование (месяцы 6–18)

### Бизнес-цели
- Подключить оставшиеся бизнес-направления (ИИ, Фарма, Оборудование).
- Запустить Data Lake для централизованной аналитики.
- Ввести Data Governance для предотвращения фрагментации данных.

### Активности

| Месяц | Активность | Роли | Результат |
|---|---|---|---|
| 6–8 | Проектирование и запуск ИИ-домена (ML-модели, GPU) | Domain Architect, ML Engineers (2) | DiagnosticResultReady в проде |
| 8–10 | Запуск Data Governance Council. Ежемесячные встречи DPO всех доменов | Data Governance Lead, все DPO | Согласованные определения, каталог Data Products |
| 10–14 | Интеграция Фарма-домена и Домена оборудования | Data Engineers (2), DPO (2) | PharmaInventory, DeviceTelemetry в проде |
| 12–15 | Развёртывание Data Lake / Lakehouse (Object Storage + YDB) | Platform Engineer, Data Engineers | Единое хранилище сырых данных |
| 14–18 | Запуск потоковых витрин (Kafka Streams / Spark) | Data Engineers | Агрегации near-real-time |
| 16–18 | Расширение Self-service BI на все домены. Обучение BI-аналитиков | BI-аналитики | 100% новых отчётов через DataLens |

### Новые роли на этапе
- Data Governance Lead.
- ML Engineers (2).
- DPO для ИИ, Фармы, Оборудования (+3).
- Data Engineers для новых доменов (+3).

### KPI успеха
- Все 5 доменов публикуют Data Products с описанным SLA.
- Data Catalog содержит ≥ 10 зарегистрированных Data Products.
- 80% новых бизнес-отчётов строятся через Self-service (без участия IT).

---

## Этап 3: Оптимизация и поддержка (месяцы 18–36)

### Бизнес-цели
- Отказаться от легаси-систем (DWH, Camel) на критическом пути.
- Достичь полной доменной автономии: каждая команда независимо развивает свой Data Product.
- Масштабироваться на 2–3 новых региона с минимальными затратами.

### Активности

| Месяц | Активность | Роли | Результат |
|---|---|---|---|
| 18–24 | Отказ от синхронных интеграций через Camel. Все критические потоки — через Kafka | Domain Architect, Data Engineers | Camel выведен с критического пути |
| 20–26 | Миграция оставшихся данных из DWH в доменные хранилища. DWH → cold storage | Data Engineers, DBA (легаси) | DWH только для исторических запросов |
| 24–30 | Внедрение GitOps (ArgoCD) для управления доменной инфраструктурой | Platform Engineer | Pull-based деплой, audit trail |
| 26–32 | Геораспределённое развёртывание: репликация Kafka и Data Products в новых регионах | Platform Engineer, Data Engineers | 2 новых региона подключены |
| 30–36 | Оптимизация затрат: автоскейлинг, резервирование облачных ресурсов | Platform Engineer, DevOps | Снижение облачных затрат на 15–20% |
| 30–36 | Непрерывное улучшение Data Products: мониторинг SLA, обратная связь от потребителей | DPO, Data Governance Lead | NPS потребителей ≥ 8/10 |

### KPI успеха
- DWH не участвует в операционных потоках: 100% данных — через доменные Data Products.
- Добавление нового региона: ≤ 2 месяцев (vs 6+ в AS-IS).
- Бюджет облака стабилизирован, рост затрат ≤ +5% в год при добавлении доменов.

## Привязка к бизнес-целям компании

| Бизнес-цель | Закрывается на этапе | Как именно |
|---|---|---|
| **Продукты: запуск новых финтех- и медицинских сервисов** | Этап 1–2 | Data Products Patient360 и FinancialCore — основа для новых сервисов |
| **Монетизация ИИ-функций** | Этап 2 | ИИ-домен → DiagnosticResultReady как платный Data Product для внешних клиник |
| **География: 2–3 новых региона** | Этап 3 | Геораспределённый Kafka + репликация Data Products |
| **Данные: near-real-time обработка** | Этап 2 | Kafka Streams + потоковые витрины |
| **Слабо-связанная событийная платформа** | Этап 1–3 | Event-Driven Architecture + Data Mesh — фундамент |
| **Снижение time-to-market** | Этап 1+ | Self-service BI: отчёты за минуты. Новый домен: за недели |
