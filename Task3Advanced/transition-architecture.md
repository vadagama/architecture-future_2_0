# Transition Architecture: миграция с ESB (Camel) на событийную платформу

## Почему «Event Bus ≠ ESB» — ключевое различие

Утверждение «Event Bus (Kafka) — замена шины Camel» требует уточнения: **Kafka не является заменой ESB 1 в 1**. Эти технологии решают принципиально разные задачи и имеют разный набор функциональности. Здесь я полностью согласен.

| Измерение | Apache Camel (ESB) | Apache Kafka (Event Bus) |
|---|---|---|
| **Природа** | Интеграционный фреймворк/шина | Распределённый event-журнал (log) |
| **Модель взаимодействия** | Синхронная (request/reply) + ограниченно асинхронная | Асинхронная (publish/subscribe) |
| **Маршрутизация** | Встроенная: content-based, recipient list, split/aggregate, dynamic router | Отсутствует «из коробки». Требует Kafka Streams / KSQL или внешних процессоров |
| **Трансформации** | Встроенные: XSLT, JSON, data mapping (любые Enterprise Integration Patterns) | Отсутствуют «из коробки». Требуют Kafka Streams, Spark или доменных сервисов |
| **Протокольная медиация** | HTTP, JMS, FTP, file, JDBC, сотни коннекторов | Ограничена Kafka Connect (source/sink). Полная медиация — через API Gateway или адаптеры |
| **Оркестрация** | Встроенная: маршруты, process definitions | Отсутствует. Оркестрация — в доменных сервисах или Saga-координаторах |
| **Бизнес-логика** | Часто встроена в маршруты (антипаттерн, но распространён) | Не содержит. Логика — исключительно в доменных сервисах |
| **Паттерны надёжности** | Retry, circuit breaker, dead letter, redelivery | Частично: DLQ, replay, consumer retry. Circuit breaker — на уровне потребителя |
| **Гарантии доставки** | At-most-once, конфигурируемо | At-least-once (по умолчанию), exactly-once (транзакционный продюсер) |

**Вывод:** переход с Camel на Kafka — это не «замена технологии», а **смена архитектурной парадигмы**: с централизованной оркестрации на децентрализованную хореографию событий. Функциональность ESB не исчезает — она перераспределяется по разным слоям целевой архитектуры.

## Куда переезжает функциональность ESB

Ниже — декомпозиция каждого типа функциональности, реализованной сегодня в Camel, с указанием её нового места в целевой архитектуре.

### 1. Маршрутизация (Routing)

| Возможность Camel | Куда переезжает | Как реализуется |
|---|---|---|
| **Content-Based Router** — направить сообщение в нужную очередь по содержимому | **Kafka Topics + Kafka Streams** | События публикуются в доменные топики по бизнес-ключу (например, `patient_id`). Потребители сами подписываются на интересующие топики. Content-based routing, если нужен, реализуется через Kafka Streams` |
| **Recipient List** — одно сообщение нескольким получателям | **Kafka Publish/Subscribe** | Нативная модель Kafka: один продюсер → топик → множество консьюмер-групп. Каждый домен — отдельная consumer group |
| **Dynamic Router** — маршрут определяется в runtime | **Доменные сервисы + Kafka** | Логика маршрутизации выносится в доменный код. Сервис решает, в какой топик публиковать, и публикует |

### 2. Трансформации (Transformations)

| Тип трансформации | Где сегодня (Camel) | Куда переезжает |
|---|---|---|
| **Потоковые трансформации** (real-time) — обогащение, фильтрация, валидация | Camel-маршруты с Java/XML DSL | **Kafka Streams / KSQL** — потоковая обработка внутри шины (`mapValues`, `transform`, `join`). Или **доменный outbound-адаптер** — преобразование до публикации |
| **Пакетные трансформации** (batch) — пересчёт витрин, агрегации за сутки | Camel + SQL-запросы к DWH | **Apache Spark / Yandex Data Proc** — тяжелые batch-преобразования над Data Lake (Spark SQL, DataFrame API) |
| **Схемная валидация** — проверка формата сообщения | Camel валидаторы (XML Schema, JSON Schema) | **Schema Registry (Avro)** — валидация схемы при публикации и потреблении. Несовместимые сообщения отклоняются брокером |
| **Форматная конверсия** — XML ↔ JSON, CSV → Avro | Camel data formats | **Kafka Connect** — Single Message Transforms (SMT). **Доменные ACL-адаптеры** — для легаси-форматов (конвертеры в Legacy Bridge) |

### 3. ФЛК — функциональные логические компоненты

Под ФЛК понимаются бизнес-правила, валидации и вычисления, встроенные в Camel-маршруты. Это один из самых проблемных аспектов легаси: бизнес-логика «размазана» по маршрутам, не тестируется изолированно и не имеет явного владельца.

| Тип ФЛК | Куда переезжает | Как |
|---|---|---|
| **Валидация бизнес-правил** (например, «сумма кредита не может превышать N для пациента категории X») | **Доменные сервисы** — в application layer домена | Use-case или domain service проводит валидацию **до** публикации события. Событие публикуется только после успешной валидации |
| **Вычислительная логика** (расчёт процентов, скоринг) | **Доменные сервисы** или **Kafka Streams** для простых вычислений | Сложная логика — в доменном сервисе. Простые преобразования (например, умножить поле на коэффициент) — в Kafka Streams |
| **Правила маршрутизации, зависящие от бизнес-контекста** | **Доменный Decision Service** — отдельный микросервис, инкапсулирующий правила | Сервис принимает решение и возвращает результат. Может использовать движок бизнес-правил (например, Drools), если правил много |
| **Обогащение мастер-данными** (справочники, классификаторы) | **Kafka Streams KTable** — материализованный справочник в топике. Или **API к Data Product** владельца справочника | KTable автоматически обновляется при изменении справочника. |

**Ключевой принцип:** ФЛК **никогда** не находится в шине. Kafka — транспорт, а не вычислительный слой. Вся бизнес-логика принадлежит доменам и выполняется либо до публикации события (продюсер), либо при потреблении (консьюмер).

### 4. Протокольная медиация (Protocol Mediation)

| Протокол/система | Где сегодня | Куда переезжает |
|---|---|---|
| **HTTP/REST** — синхронные API-вызовы | Camel HTTP component | **Kong API Gateway** — единая точка входа для синхронных запросов. Маршрутизация, rate limiting, аутентификация |
| **Файловый обмен** (CSV, Excel из общих папок) | Camel File component | **Kafka Connect FileSource / S3 Source** — файлы загружаются в топики Kafka автоматически при появлении. **Data Lake** — единое место для сырых файлов |
| **FTP/SFTP** | Camel FTP component | **Kafka Connect FTP Source Connector** — потоковая загрузка файлов в топики. Параллельно — миграция контрагентов на API (цель к концу 3-го года) |
| **JDBC (прямые запросы к DWH)** | Camel JDBC component | **Kafka Connect JDBC Source Connector** — CDC (Change Data Capture) из легаси-DWH в Kafka. **Legacy Bridge** — для данных, которые ещё не мигрированы |
| **JMS / MQ** | Camel JMS component | **Kafka Connect JMS Source/Sink** — интеграция с JMS-системами на переходный период. Выводятся по мере отказа от легаси |
| **gRPC** (межсервисное взаимодействие для низких задержек) | Отсутствует в AS-IS | **gRPC напрямую** между доменными сервисами — для сценариев, где асинхронная доставка через Kafka неприемлема (например, проверка доступности врача при записи) |

**Принцип:** синхронные вызовы (HTTP, gRPC) — через API Gateway. Асинхронные/файловые интеграции — через Kafka Connect. Прямые протокольные адаптеры в Camel-стиле не создаются.

### 5. Паттерны надёжности (Reliability Patterns)

| Паттерн | Реализация в Camel | Реализация в TO-BE |
|---|---|---|
| **Retry (повтор)** | Camel `onException().maximumRedeliveries()` | **Kafka Consumer Retry** — нативный механизм повторной обработки. Нелинейный backoff. Исчерпание попыток → DLQ. |
| **Circuit Breaker** | Camel `circuitBreaker()` | **Resilience4j / Hystrix** в доменных сервисах (Go/Java). Либо **Kong API Gateway** — для синхронных вызовов. Не в шине |
| **Dead Letter Channel** | Camel `deadLetterChannel()` | **Kafka DLQ (специальные dead-letter-топики)** — события, не обработанные после N попыток. |
| **Idempotent Consumer** | Camel `idempotentConsumer()` | **Idempotency Key** в заголовке события (`event_id` UUID) + проверка на дубликат в БД потребителя |
| **Message Store (гарантированная доставка)** | Camel persistence | **Kafka retention** (настраиваемый срок хранения, по умолчанию 7 дней). **Kafka log compaction** — для событий с ключом, где важно последнее состояние. |
| **Outbox Pattern** | Отсутствует (ручная реализация) | **Transactional Outbox** — атомарная запись в БД + публикация события (INSERT в outbox-таблицу + Debezium/CDC в Kafka). Исключает потерю события при сбое |
| **Saga (распределённая транзакция)** | Camel встроенные компенсации | **Choreography Saga** на событиях: каждый шаг — доменное событие. Компенсация — через обратное событие (например, `PaymentReversed`). Доменные сервисы координируются без центрального оркестратора |

### 6. Интеграционная и бизнес-логика

| Тип логики | Где сегодня | Проблема AS-IS | Куда переезжает |
|---|---|---|---|
| **Интеграционная логика** (adapt, transform, route) | Camel-маршруты | Логика «склеена» с транспортом. Изменение формата = правка маршрута + регрессионное тестирование всех зависимостей | **Kafka Connect** — для source/sink адаптеров. **Legacy Bridge (ACL-слой)** — для легаси-форматов. **Kafka Streams** — для потоковых преобразований. Всё версионируется и тестируется изолированно |
| **Бизнес-логика** (правила, расчёты, валидации) | Хранимые процедуры DWH + Camel-маршруты | Бизнес-правила не имеют явного владельца. Изменение в одном месте ломает отчёты других доменов | **Доменные сервисы** — каждая бизнес-операция инкапсулирована в домене-владельце. Владелец отвечает за корректность и SLA |
| **Оркестрация процессов** (например, выдача кредита: проверить пациента → открыть счёт → создать график платежей) | Camel route с вызовами нескольких систем | Маршрут синхронный, любая ошибка = откат вручную. Добавление шага = изменение маршрута | **Saga (Choreography)** через события. |
| **Аналитические расчёты** (агрегации, витрины) | Хранимые процедуры DWH + Power BI | Часы на выполнение. Конкуренция за ресурсы DWH с операционными запросами | **Kafka Streams / Spark** — потоковые витрины (минуты). **Data Lakehouse** — тяжёлые batch-расчёты на выделенных ресурсах без влияния на операционку |

### Конкретный план миграции Camel-маршрутов

| Приоритет | Тип маршрута | Стратегия замены | Инструмент |
|---|---|---|---|
| **1. High** | Маршруты, публикующие данные в DWH | Данные публикуются в Kafka-топик вместо JDBC-вставки. Потребители читают из Kafka. DWH наполняется через Kafka Connect Sink (на переходный период) | Kafka Connect JDBC Sink |
| **2. High** | Синхронные вызовы между доменами | Замена на асинхронные события. Синхронный ответ заменяется подпиской на результат. Если синхронность критична — gRPC через API Gateway | Kafka + Kong API Gateway |
| **3. Medium** | Файловые обмены (CSV, Excel) | Kafka Connect File Source → топик. Потребители читают из топика. Отправители мигрируют на API | Kafka Connect + доменные API |
| **4. Medium** | Трансформационные маршруты (XSLT, JSON mapping) | Kafka Streams (поток) или Spark (batch). Логика трансформации переписывается как независимый микросервис | Kafka Streams / Spark |
| **5. Low** | Маршруты-заглушки, legacy-форматы | Legacy Bridge публикует как есть. Потребители используют ACL-адаптер до полной миграции поставщика | Legacy Bridge (временный) |
| **6. Low** | Маршруты, обслуживающие только PowerBuilder | Выводятся вместе с PowerBuilder. UI заменяется на React, данные — через доменные API | Не мигрируются. Отключаются |

## Заключение

Переход с Apache Camel на событийную платформу на базе Kafka — это **не технологическая замена**, а **архитектурная трансформация**:

- **Маршрутизация** переезжает в модель pub/sub Kafka-топиков и Kafka Streams.
- **Трансформации** разделяются: потоковые — в Kafka Streams/KSQL, пакетные — в Spark/Data Proc, схемные — в Schema Registry.
- **ФЛК и бизнес-логика** переезжают в доменные сервисы — им там и место, в шине им быть не должно.
- **Паттерны надёжности** реализуются комбинацией нативных механизмов Kafka (DLQ, retry, replay) и доменных библиотек (Resilience4j, Outbox).
- **Протокольная медиация** распределяется между Kafka Connect (файлы, БД, легаси) и Kong API Gateway (HTTP, gRPC).

Центральный принцип: **Kafka — транспорт, а не вычислительный слой**. Вся логика, трансформации и оркестрация принадлежат доменам-владельцам, а не шине.
